# UC7. Проверить заказ (клиент)

Детальное описание варианта использования по системе «Модель системы 2026.drawio».

## Таблица 1 — Детальное описание варианта использования UC7

| UC7 | Поле | Содержимое |
|---|---|---|
| | **Название** | Проверить заказ (клиент) |
| | **Описание** | Клиент проверяет состав своего заказа, связанные счета, текущий статус и сведения о доставке |
| | **Основная задача** | Проверка клиентом сведений о ранее созданном заказе |
| | **Цель** | Обеспечить клиенту возможность оценить правильность сведений о заказе и определить состояние его выполнения |
| | **Актёры** | 1. Клиент (Инициатор)<br>2. Оператор (Участник альтернативного потока 1.1 и исключения 1) |
| | **Предусловие** | Клиент запрашивает сведения о своём заказе, указав его идентификатор |
| | **Постусловие** | Клиентом проверены состав заказа, сведения о счетах и транзакциях, выяснены статус заказа и доступные сведения о доставке |
| | **Основной поток** | 1. Клиент проверяет состав заказа<br>2. Клиент проверяет счета заказа<br>3. Клиент проверяет статус заказа и сведения о доставке |
| | **Альтернативы** | 1.1. Состав заказа требует разъяснения<br>2.1. Счета ещё не выставлены<br>3.1. Доставка ещё не оформлена или курьер не назначен |
| | **Исключения** | 1. Получить сведения о заказе невозможно |

## Таблица 2 — Детализация потоков событий

| Поток | Подсобытие или условие | Содержимое |
|---|---|---|
| **Основной 1. Проверить состав заказа** | **а. Предусловие** | Клиент запрашивает сведения о своём заказе, указав его идентификатор |
| | **б.** | Система предоставляет идентификатор заказа и перечень товаров, зарегистрированный при оформлении |
| | **в.** | Клиент сопоставляет перечень товаров с составом, указанным при оформлении |
| | **г. Постусловие** | Нужный заказ определён, его состав проверен клиентом, неразрешённых расхождений нет |
| **Основной 2. Проверить счета заказа** | **а. Предусловие** | Клиент запрашивает счета выбранного заказа, состав которого проверен |
| | **б.** | Система предоставляет связанные с заказом счета, их суммы и сведения о зарегистрированных транзакциях. В основном сценарии выставлен хотя бы один счёт |
| | **в.** | Клиент проверяет принадлежность счетов выбранному заказу, их суммы и сведения о транзакциях либо отсутствие зарегистрированных транзакций |
| | **г. Постусловие** | Клиентом проверены сведения о счетах и транзакциях выбранного заказа либо установлено, что счета ещё не выставлены |
| **Основной 3. Проверить статус заказа и сведения о доставке** | **а. Предусловие** | Клиент запрашивает статус и сведения о доставке выбранного заказа, состав которого проверен, а счета проверены либо установлено их отсутствие |
| | **б.** | Система предоставляет текущий статус заказа и сведения о связанной с ним доставке, курьере и маршруте. В основном сценарии доставка оформлена и курьер назначен |
| | **в.** | Клиент выясняет текущий статус заказа, проверяет его включение в доставку и знакомится с доступными сведениями о курьере и маршруте |
| | **г. Постусловие** | Клиентом выяснен статус заказа и доступные сведения о доставке либо установлено, какие сведения пока отсутствуют. Проверка заказа завершена |
| **Альтернатива 1.1. Состав заказа требует разъяснения** | **а. Условие возникновения** | В подсобытии «в» основного потока 1 клиент не может однозначно сопоставить перечень товаров с составом своего заказа |
| | **б.** | Клиент обращается к оператору и указывает, что требует уточнения |
| | **в.** | Оператор разъясняет зарегистрированный состав |
| | **г.** | Клиент повторно сопоставляет товары |
| | **д. Продолжение** | Если расхождений нет, достигнуто постусловие основного потока 1; клиент переходит к потоку 2. Если расхождение сохраняется, клиент прекращает проверку и отдельно переходит к UC10. Успешное постусловие UC7 не достигается; после изменения заказа проверка начинается заново |
| **Альтернатива 2.1. Счета ещё не выставлены** | **а. Условие возникновения** | В подсобытии «б» основного потока 2 установлено, что у выбранного заказа нет выставленных счетов |
| | **б.** | Система сообщает клиенту, что счета по заказу ещё не выставлены |
| | **в.** | Клиент знакомится с сообщением и устанавливает, что суммы и транзакции пока отсутствуют для проверки |
| | **г. Продолжение** | Достигнуто постусловие основного потока 2; клиент переходит к основному потоку 3 |
| **Альтернатива 3.1. Доставка ещё не оформлена или курьер не назначен** | **а. Условие возникновения** | В подсобытии «б» основного потока 3 установлено, что доставка ещё не оформлена либо курьер не назначен |
| | **б.** | Система предоставляет текущий статус заказа, имеющиеся сведения о доставке и сообщает, какие сведения пока отсутствуют |
| | **в.** | Клиент проверяет доступную информацию и выясняет текущее состояние доставки |
| | **г. Продолжение** | Достигнуто постусловие основного потока 3; проверка завершается |
| **Исключение 1. Получить сведения о заказе невозможно** | **а. Условие возникновения** | При подготовке ответа в подсобытии «б» основного потока 1 система не может предоставить клиенту сведения о заказе |
| | **б.** | Клиент обращается к оператору, сообщает идентификатор заказа и описывает проблему |
| | **в.** | Оператор проверяет принадлежность заказа клиенту и выясняет причину недоступности сведений |
| | **г.** | Оператор сообщает клиенту результат проверки и доступный способ продолжения |
| | **д. Продолжение** | Если возможность получения сведений восстановлена, клиент повторяет запрос — возврат к подсобытию «б» основного потока 1. Иначе клиент прекращает текущую проверку; постусловие потока 1 не достигнуто, потоки 2 и 3 не выполняются |

## Таблица 3 — Обоснование принятых решений (не для отчёта)

| Решение | Обоснование |
|---|---|
| Структура таблицы описания соответствует UC6 | Сохранены поля названия, описания, основной задачи, цели, актёров, условий, основного потока, альтернатив и исключений. В первой таблице перечислены названия потоков; во второй раскрыты основные потоки, альтернативы и исключение |
| UC7 описывает проверку сведений о заказе | Сохранена трактовка ранее созданного UC7. В PDOM у заказа указаны товары, счета и статус, а клиент получает и отслеживает доставку. Физическая проверка передаваемых товаров в данное описание не включена |
| Связь UC2 → UC7 не объявлена как include | В пояснениях к UC6 упоминается проверка при доставке, но страница UC исходной модели содержит список названий без такой связи. Одного упоминания недостаточно, чтобы менять границы UC7 или вводить отношение включения |
| Клиент — Инициатор | Именно клиент начинает проверку и действует во всех трёх основных потоках. Описание отражает взаимодействие с точки зрения пользователя, как требуется в §8 и §15 конспекта Л02 |
| Оператор — Участник альтернативы 1.1 и исключения 1 | Оператор разъясняет состав заказа, а при недоступности сведений выясняет причину и сообщает клиенту способ продолжения. Это соответствует его участию в обслуживании клиента в PDOM; в обычной проверке его участие не требуется |
| Курьер, предприятие и система не добавлены в актёры UC7 | Курьер и предприятие не выполняют действий в описанных потоках. Сама рассматриваемая система не является внешним актёром; её ответ явно выделен в подсобытии «б» как реакция на запрос клиента |
| Цель отличается от постусловия | Цель обозначает пользу для клиента; постусловие перечисляет проверяемые результаты успешного выполнения, как в §13 конспекта Л02 |
| Три последовательных потока по четыре подсобытия | Применена единая последовательность: клиент уже сделал запрос, система предоставляет сведения, клиент их проверяет, результат проверки зафиксирован постусловием. Ответ системы и проверка клиентом разделены, поскольку у них разные исполнители |
| Предусловие указывает инициирующее обращение | Запрос клиента обозначает момент начала обработки. Для потоков 2 и 3 также указан результат предыдущей проверки, необходимый для продолжения |
| Между потоками сохранена логическая связь условий | Проверенный состав позволяет перейти к счетам выбранного заказа; проверка счетов или установление их отсутствия позволяет перейти к статусу и доставке. Начало следующего потока инициируется новым запросом клиента, поэтому предусловие не повторяет предыдущее постусловие дословно |
| Нет кнопок, экранов, списков интерфейса и деталей хранения | Лекция Л02 (§14, §18) требует описывать внешнее поведение системы. Раздел методички «Ограничения вариантов использования» рекомендует не подменять прецеденты описанием интерфейса |
| У каждой альтернативы указаны условие и точка продолжения | Это следует из §15–16 конспекта Л02. Альтернатива 1.1 возвращает проверку в основное русло; 2.1 и 3.1 позволяют завершить соответствующий поток при допустимом отсутствии данных |
| Альтернатива 1.1 охватывает расхождение, устранимое разъяснением | Постусловие основного потока 1 достигается только после повторного сопоставления, когда клиент убедился в отсутствии расхождений. Если требуется изменение заказа, клиент прекращает текущую проверку и отдельно обращается к UC10; после изменения проверка начинается заново. Успешное постусловие при неразрешённом расхождении не объявляется |
| Отсутствие счетов и доставки отделено от сбоя | У заказа может ещё не быть счетов или доставки. Полученное подтверждение их отсутствия — допустимый результат проверки. Невозможность получить сведения не позволяет делать такой вывод |
| Исключение допускает восстановление или завершение без успеха | По §16 лекции исключительный поток может вернуть выполнение в нормальное русло либо корректно завершить его. После обращения к оператору клиент возвращается к подсобытию «б» основного потока 1, если сведения снова доступны; иначе прекращает проверку без достижения успешного постусловия. Проверка принадлежности заказа не позволяет предоставлять клиенту чужие данные |
| Оплата, изменение и подтверждение получения не выполняются | UC4, UC10 и доставка заказа описываются отдельно. Проверка сведений не изменяет заказ и не дублирует чужие потоки; из возможного перехода к другому UC не выводится автоматически отношение include или extend |
| Отсутствие транзакции не приравнивается к доказанной неоплате | Клиент устанавливает только отсутствие зарегистрированной транзакции. Проверка не создаёт платёж и не меняет его состояние |
| Сведения о маршруте не обещают точное время прибытия | В модели у маршрута указаны длина и время; из этих полей нельзя без дополнительных требований вывести гарантированный срок прибытия к конкретному клиенту |

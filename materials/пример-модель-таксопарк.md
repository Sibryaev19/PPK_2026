# Пример модели системы («Таксопарк») — эталон для проекта

> **Источник:** `Модель системы 2025.drawio` (этот же каталог) (5 страниц). Это пример преподавателя того, какой комплект моделей ожидается от проекта по курсу: PDOM + IDEF0 (А-0, А0) + DFD + диаграмма последовательностей. Предметная область примера — система заказа такси.
> Рисуется в draw.io; классы — стандартные UML-прямоугольники с секциями; у IDEF0/DFD использованы подписи узлов/дуг и нумерация (А-0, A0, A1–A4, D1–D3).

## Страница 1. PDOM (диаграмма классов)

Классы (с атрибутами и операциями, выжимка из файла):

| Класс | Атрибуты (примеры) | Операции (примеры) |
|---|---|---|
| Заказ | id: Int, status: String, cost: Float, createdAt: DateTime, passengerCount: Int | +changeStatus() |
| Маршрут | id: Int, startPoint: GeoPoint, endPoint: GeoPoint | +recalculateRoute() |
| Транзакция | id: Int, amount: Float, status: String, paymentMethod: String, paymentTime: DateTime | +processPayment(), +refundPayment() |
| Таксопарк | id: Int, totalCars: Int, name: String, contactPhone: String | +addTaxi(), +removeTaxi() |
| Такси | id: Int, licensePlate: String, currentLocation: GeoPoint, model, carClass, color, status: String, phoneNumber | +updateStatus(), +updateLocation() |
| Диспетчер | id: Int, … | … |

Ассоциации с глагольными подписями (в духе «роли/смысл связи»): Проверяет, Содержит, Контролирует, Производит, Выполняет, Передаёт заказ, Определяет, Имеет, Создаёт, Получает, Вызывает, Использует, Формирует.

**Стиль:** имена классов — существительные предметной области; атрибуты с префиксом видимости (`-`, `+`) и типами (`Int`, `String`, `Float`, `DateTime`, `GeoPoint`); операции — глагольные методы с `()`.

## Страница 2. IDEF0: контекстная диаграмма А-0

- Узел: **А-0 «Управлять таксопарком»** (заголовок «Такси»).
- Входы (I): I1, I2, I3 — Заказ и др.
- Выходы (O): O1 — Отчёт.
- Управление (С): С1 — Тариф, С2 — Регламент, С3–С5.
- Механизмы (М): М1 — ГИС, М2–М3, М4 — Платежная система, М5; исполнители: Клиент, Водитель.

## Страница 3. IDEF0: декомпозиция А0

А0 «Управлять таксопарком» раскрывается на 4 функции:

| Номер | Функция |
|---|---|
| A1 | Контролировать клиента |
| A2 | Обработать запрос |
| A3 | Выполнить заказ |
| A4 | Контролировать водителя |

Дуги: Запрос, Регламент, Водитель, ГИС, Платежная система и т.д. между функциями — типовой IDEF0-поток.

## Страница 4. DFD (диаграмма потоков данных)

- Внешние сущности: Клиент, Такси, Платежная система, ГИС, Геолокация.
- Процессы (нумерация согласована с IDEF0 A1–A4): 1. Контролировать клиента; 2. Обработать запрос; 3. Выполнить заказ; 4. Контролировать водителя.
- Накопители данных: D1 — База данных таксистов; D2 — База данных заказов; D3 — База данных клиента.
- Потоки: Информация о заказе, Информация о такси, Статус заказа, Данные по заказу, Данные эквайринга, Статус такси, Информация о клиенте, Запрос, Заказ, Правила предоставления услуг и др.

## Страница 5. UML-диаграмма последовательности

- Линии жизни (lifeline): Запрос, Заказ, Маршрут, Такси, Контроллер (+ :Object).
- Сообщения: `Создать()` (к Заказу, к Маршруту), `dispatch` / `return` (между Контроллером, Такси, Заказом), «Заказ», «Ожидание», «Ответ»; extensively используются примечания (Note).

## Выводы для нашего проекта (что взять за образец)

1. Комплект = PDOM (классы предметной области) + IDEF0 А-0/А0 (4 функции декомпозиции) + DFD (те же 4 процесса, внешние сущности, D1–D3) + sequence (сценарий основного варианта использования).
2. Нумерация процессов сквозная: A1–A4 (IDEF0) = 1–4 (DFD).
3. Атрибуты классов типизированы, с видимостью; ассоциации подписываются глаголами.
4. IDEF0 требует входов/выходов/управления/механизмов на каждом уровне; контекст — одна функция А-0.
5. Последовательность рисуется по линиям жизни с `вызов()` и `return`.

# PDOM «МедЭксперт» — расшифровка диаграммы (КТ-1)

> Расшифровка диаграммы [../diagrams/PPK_PDOM_KT1.drawio](../diagrams/PPK_PDOM_KT1.drawio) для текста отчёта и защиты. Сами материалы ЛР1 — в [Контрольная точка 1.md](Контрольная%20точка%201.md).

Принципы модели:

1. Управляющие сущности между собой **не связаны** — любое взаимодействие проходит только через управляемые сущности (данные).
2. У каждой управляющей сущности **глаголы связей не повторяются**: «получает», «запрашивает», «оформляет» — разные действия.
3. Клиентский модуль на диаграмме подписан «Врач»: для системы человека нет, есть АРМ врача.

## Управляющие сущности (5)

| № | Сущность | Тип | Роль |
|---|---|---|---|
| У1 | Врач | клиентский модуль (АРМ, 0..n) | вводит данные приёма, подтверждает диагноз, утверждает план |
| У2 | Внешняя МИС | внешняя сущность (A1, A2) | поставляет медкарты пациентов |
| У3 | Модуль регистрации | серверный модуль (1) | оформляет обследование (A1) |
| У4 | Модуль диагностики | серверный модуль (1) | формирует диагноз (A2) |
| У5 | Модуль лечения | серверный модуль (1) | дополняет обследование лечением (A3) |

## Управляемые сущности (6)

| № | Сущность | Атрибуты | Пояснение |
|---|---|---|---|
| С1 | Данные пациента | ФИО, дата рождения, номер полиса | разовый ввод «кто пришёл»; вход I1 |
| С2 | Медкарта | анкетные данные, хронические заболевания, аллергии, прошлые диагнозы | целиком живёт в МИС, система её только читает |
| С3 | Показание | источник (врач или прибор), показатель/симптом, значение, единицы, флаг отклонения | обобщённые «показания приборов»: врач-человек тоже выступает прибором (жалобы, симптомы осмотра); входы I2+I3 |
| С4 | Предварительный диагноз | название болезни, обоснование, уверенность, статус (предложен/подтверждён) | рейтинг гипотез = несколько кандидатов со статусом «предложен»; выход O2 |
| С5 | Обследование | дата/время, статус, заключение, назначения | итоговый документ случая: оформляется (A1) и дополняется (A3); выход O1 |
| С6 | План лечения | методика, назначения, срок, рекомендации, статус (проект/утверждён), рецепт | выход O3 |

## Связи по управляющим

**У1 Врач**
- вводит → С1 Данные пациента
- фиксирует → С3 Показание (приборные измерения и симптомы от врача)
- подтверждает → С4 Предварительный диагноз (выбор из рейтинга гипотез)
- просматривает → С5 Обследование (итоговый документ случая)
- утверждает → С6 План лечения (корректировка и утверждение проекта)

**У2 Внешняя МИС**
- поставляет → С2 Медкарта

**У3 Модуль регистрации (A1)**
- получает → С1 Данные пациента
- запрашивает → С2 Медкарта (по данным пациента)
- оформляет → С5 Обследование (собирает карту и показания в единый документ)

**У4 Модуль диагностики (A2)**
- считывает → С3 Показание
- принимает → С2 Медкарта (полученную на этапе A1)
- формирует → С4 Предварительный диагноз

**У5 Модуль лечения (A3)**
- использует → С4 Предварительный диагноз (подтверждённый)
- составляет → С6 План лечения
- дополняет → С5 Обследование (вписывает утверждённый план)

## Агрегации (ромбы на диаграмме)

- С5 Обследование ◇— Содержит С4 Предварительный диагноз
- С5 Обследование ◇— Включает С6 План лечения

## Цепочка по этапам

```
A1:  Врач ─вводит─► С1 ─получает─► У3;  У2 ─поставляет─► С2 ◄─запрашивает─ У3
     Врач ─фиксирует─► С3;  У3 ─оформляет─► С5
A2:  У4 ─считывает─► С3, ─принимает─► С2, ─формирует─► С4;  Врач ─подтверждает─► С4
A3:  У5 ─использует─► С4, ─составляет─► С6, ─дополняет─► С5;  Врач ─утверждает─► С6
```

## Пояснения (чего на PDOM нет и почему)

- **Нет D1 (местной БД).** Хранилище — не сущность PDOM; оно появится на DFD как накопитель D1.
- **Нет Анамнеза.** Жалобы и симптомы осмотра — это показание, у которого источником выступает врач («врач как прибор»). Одно поле «источник» закрывает и приборные, и врачебные данные.
- **Нет РеференсныхНорм.** Сверка с нормами уже даёт «флаг отклонения» в атрибутах Показания; сами нормы — в словаре данных и на IDEF0.
- **Нет Аптечного сервиса и Схожих случаев.** Это содержимое внешних систем за рамками КТ-1: подбор препаратов (A3-2) и поиск схожих случаев (A2-3) появятся на IDEF0/DFD как дуги от внешних сущностей. На PDOM показаны только сущности, с которыми непосредственно работают модули.
- **Обследование диагностике не нужно.** Модуль диагностики работает с первородными данными (показания, карта), а не с чужим отчётом. Обследование — документ случая: его оформляет регистрация (A1) и дополняет лечение (A3).
- **Обратная связь при слабом рейтинге** (врач возвращается за дополнительными показаниями) — возврат к A1 в сценарии; на PDOM не отображается, будет дугой на IDEF0.

## Что из модели видно (для защиты)

- Управляющие не связаны между собой ни одним ребром — модули взаимодействуют только через данные, любой модуль заменяем.
- Клиент-серверность: Врач (АРМ) — много экземпляров, каждый серверный модуль — один; «много клиентов — один обработчик».
- Конвейер С1/С3 → С5 → С4 → С6 = A1 → A2 → A3; входы I1–I3 и выходы O1–O3 диаграммы А-0 ложатся на сущности.
